# C-01 — le contrat de date rejette les dates qu'Odoo produit réellement

**Relevé en vérifiant le parcours Client dans un vrai navigateur (D38), le 24 août.**

## Ce qui a été observé

Parcours réel, contre la vraie pile (`make up`), jeton réel (`mock-google-identity` +
`/auth/google`), chauffeur réel en ligne. L'estimation réussit (`POST /quote`, 200). La
sélection d'un chauffeur déclenche `POST /rides` (création de la course) puis
`POST /rides/{id}/select-driver`. **`POST /rides` réussit réellement — 201, une vraie
`babana.ride` créée en base — mais l'application affiche « Une erreur inattendue s'est produite »**
et ne progresse jamais vers l'écran d'attente. Le journal du service temps réel et les requêtes
réseau montrent ensuite plusieurs rejeux du même appel, tous en échec (500), jusqu'à épuisement
des tentatives.

## Cause : `IsoDateTimeSchema` exige un fuseau, Odoo n'en écrit aucun

`packages/contracts/src/http/common.ts` :

```ts
export const IsoDateTimeSchema = z.string().datetime({ offset: true });
```

Odoo sérialise ses `fields.Datetime` en ISO **sans aucune indication de fuseau** — vérifié sur la
réponse réelle de `POST /rides` : `"createdAt": "2026-08-22T06:38:44.673009"`. Vérifié aussi avec
le `zod` réel du dépôt :

```js
const { z } = require('zod');
z.string().datetime({ offset: true }).safeParse('2026-08-22T06:38:44.673009');
// => { success: false, ... "Invalid datetime" }
```

**Chaque réponse qui porte un champ de ce type échoue donc sa propre validation côté client** —
`createdAt` sur `POST /rides`, et par construction tout champ du même type ailleurs
(`expiresAt` de `/quote`, `proposalExpiresAt` de `/select-driver`, etc.) : `IsoDateTimeSchema` est
une seule définition partagée (D17), le défaut n'est donc pas local à un endpoint.

`packages/api-client/src/http/client.ts::attemptOnce` fait `return
endpoint.responseSchema.parse(payload)` **après** avoir vérifié `response.ok` — la requête HTTP a
donc déjà pleinement réussi quand le `ZodError` est levé. L'écriture a eu lieu ; c'est la lecture
de sa confirmation qui échoue.

## Un second défaut amplifie le premier

`request()`, dans le même fichier :

```ts
const retryable = error instanceof ApiError ? isRetryableStatus(error.status) : true;
```

Un `ZodError` n'est pas une `ApiError` : il tombe dans la branche « erreur réseau », pensée pour
un `fetch` qui lève avant toute réponse — pas pour un succès HTTP dont la validation de charge
utile échoue après coup. Le client **rejoue** alors l'appel, avec la même `Idempotency-Key`
(l'intention d'idempotence est correcte). Mais le rejeu échoue côté Odoo avec un 500 plutôt que de
renvoyer la réponse déjà produite — signe d'un défaut distinct dans le rejeu par idempotence côté
Odoo, jamais exercé jusqu'ici pour la même raison que ci-dessous. Résultat observé : un 201 réel,
puis des 500 en boucle jusqu'à épuisement des tentatives, et l'utilisateur ne voit que l'échec
final.

## Pourquoi aucune suite existante ne l'a vu

Vérifié par lecture, pas supposé :

- Les tests Jest des écrans (`apps/client/src/screens/__tests__/*.test.tsx`) simulent
  `apiClient.request` entièrement (`jest.mock('../../auth', ...)`) — ils ne passent jamais par
  `createHttpClient` ni par `endpoint.responseSchema.parse`.
- Les tests de `packages/api-client` construisent eux-mêmes les réponses simulées, déjà au bon
  format (`Z` en fin de chaîne) — ils ne reproduisent jamais le format qu'Odoo écrit réellement.
- Les scénarios de bout en bout (`test/concurrency/*`, via `test/concurrency/helpers/
  odoo-session.ts`) parlent en `fetch` brut, pas par `@babana/api-client` — aucune validation de
  schéma de réponse n'y a jamais lieu.

**Aucune suite du dépôt n'exerce donc, en même temps, le vrai Odoo, le vrai `@babana/api-client`
et sa vraie validation de schéma.** C'est exactement la même famille de défaut que celle qui a
justifié le critère d'acceptation 5 de C-01 (« un test de bout en bout... aucune suite propre à un
service ne peut le remplacer ») — sauf que ce critère couvre l'authentification WebSocket
(`/auth/google` + connexion temps réel), pas les écritures REST. Un vrai navigateur, ce soir, a
joué ce rôle pour la première fois sur ce chemin précis.

## Ce que ça change

La commande d'une course — le geste central du produit — échoue **dès le premier appel réel**,
sur la vraie pile, pas seulement dans l'export web : `POST /rides` avec un jeton réel est le même
chemin pour l'app native. Ce n'est pas un défaut d'écran (L6-07/L3-08), c'est un défaut du socle
partagé par toutes les écritures.

## Options considérées, aucune tranchée ce soir

1. **Assouplir `IsoDateTimeSchema`** pour accepter une chaîne sans fuseau (`z.string().datetime()`
   sans `offset`, ou une regex plus permissive). Rapide, mais fait porter au client la charge
   d'accepter une ambiguïté de fuseau qu'Odoo ne devrait pas produire (un datetime sans fuseau
   n'est pas *faux*, il est *incomplet* — la spécification exige un format univoque justement
   pour éviter cette ambiguïté).
2. **Faire écrire à Odoo des dates avec fuseau explicite** (UTC, `Z` en suffixe) à la source —
   respecte la lettre du contrat, mais touche potentiellement tout endroit où Odoo sérialise une
   date vers le contrat mobile, pas seulement `POST /rides` : périmètre à cartographier avant de
   toucher quoi que ce soit.
3. **Corriger la classification retryable** (`client.ts::request`) pour ne rejouer que sur une
   vraie erreur réseau (le `fetch` a levé) ou un statut HTTP ≥ 500, jamais sur une exception de
   validation de la réponse. Nécessaire dans tous les cas, indépendamment de l'option 1 ou 2 :
   sans elle, tout futur défaut de schéma continuera de produire des écritures rejouées à l'aveugle.
4. **Diagnostiquer et corriger le rejeu par idempotence côté Odoo** (pourquoi une deuxième
   requête avec la même `Idempotency-Key` ne renvoie pas la réponse mise en cache) — un défaut
   séparé, découvert seulement parce que le défaut 1 déclenche des rejeux qui n'auraient jamais dû
   avoir lieu.

Aucune de ces quatre n'a été appliquée ce soir : elles touchent un mécanisme partagé par tous les
endpoints d'écriture, dans trois fichiers différents (`packages/contracts`, `packages/api-client`,
un contrôleur Odoo à identifier), sur un chemin qui touche l'idempotence des écritures — la liste
de `CLAUDE.md` qui demande une validation humaine avant fusion. Une réparation hâtive à cette
heure-ci sur ce chemin précis serait exactement le genre de raccourci que le protocole d'écart
existe pour éviter.

## Ce qui reste ouvert

- Les quatre options ci-dessus, à trancher avant de rouvrir L6-09 ou tout autre écran qui écrit.
- Vérifier si d'autres champs `IsoDateTimeSchema` ont déjà, par accident, été testés avec un
  format `Z`-suffixé fabriqué à la main dans un test — ce qui masquerait le même défaut ailleurs.
- Une fois corrigé : rejouer la vérification navigateur de ce soir jusqu'au bout (refus, nouvelle
  liste, sélection, ce que L3-08 vient d'ajouter) — bloquée ce soir avant même d'atteindre ce point.
