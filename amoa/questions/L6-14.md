# Écart — L6-14 : la réponse d'encaissement ne dit ni le plafond, ni si le chauffeur est passé hors ligne (J23)

Vérifié dans le code, pas supposé.

## 1. « Passé hors ligne » est inféré, pas dit

`SettleRideResponse` (`packages/contracts/src/http/settlement.ts`) :
`{ rideId, state, amountCollected, driverCashBalance }`. Rien qui dise si cet encaissement a
franchi le plafond.

Côté Odoo (`babana_ride_state.py::action_settle`), franchir le plafond **n'est pas une erreur** :
la transition réussit, le compte courant est incrémenté, `_babana_apply_cash_limit()` met le
chauffeur hors ligne, et `notify_cash_limit_reached` part vers le service temps réel. `action_settle`
renvoie `self` normalement. `CASH_LIMIT_REACHED` figure pourtant dans `SettleRideErrors` — mais
`_settle_ride` (`controllers/ride.py`) ne le lève jamais.

Résultat : pour savoir s'il doit afficher « vous êtes passé hors ligne » et proposer la remise
(critère 3 de L6-14), l'écran **compare `driverCashBalance` au plafond** — un plafond qu'il doit
d'abord aller chercher (point 2). C'est exactement le motif que cette nuit corrige ailleurs (D49,
D50) : là où l'app devine, il manque un champ.

**Proposition** : `SettleRideResponse` porte `wentOffline: boolean` (ou `cashLimitReached`),
renseigné depuis le `cash_limit_crossed` déjà calculé par `action_settle`. L'écran n'infère plus
rien.

## 2. La marge avant plafond n'est pas dans la réponse

`SettleRideResponse` donne le nouveau solde mais pas le plafond, donc pas la marge restante
(critère 2 de L6-14 : « le nouveau solde et la marge s'affichent après confirmation »).

Ce soir : après un encaissement réussi, l'écran fait un second appel `GET /drivers/me/cash`
(`driverCash`, déjà au contrat, renvoie `{ balance, limit, collectedToday }`) et affiche
`limit - balance`. Si ce second appel échoue (réseau), le nouveau solde reste affiché, pas la
marge.

**Proposition** : ajouter `cashLimit` (et/ou `marginRemaining`) à `SettleRideResponse` — la donnée
est disponible dans la même transaction, le second aller-retour disparaît. Cohérent avec L5-07
(« les données sont lues côté serveur, jamais dérivées localement »).

## 3. La file hors connexion qui survit à un redémarrage est L6-16, non construite

Critère 4 : « La confirmation hors connexion est mise en file et rejouée (L6-16). » `L6-16`
(`packages/api-client/src/offline/`, file d'écriture persistante générique) n'existe pas. Le seul
mécanisme de file présent est `PendingIncidentQueue`, typé pour les alertes d'incident, pas
réutilisable tel quel pour un `POST /rides/{id}/settle`.

Ce soir : sur échec réseau, l'écran passe en état « en attente », conserve **la même clé
d'idempotence** (`generateIdempotencyKey` une fois par montage d'écran) et propose « Réessayer
maintenant ». Un renvoi ne produit jamais de double encaissement (critère 5 — clé stable + cache
`babana.idempotency.record` côté Odoo, vérifié en test). Ce qui manque : la persistance qui
survit à la fermeture de l'app et le rejeu automatique à la reconnexion — c'est le périmètre de
L6-16, pas de cet écran. `SettlementScreen` est prêt à s'appuyer sur cette file le jour où elle
existe (même patron que `EmergencyButton` avec `pendingIncidentQueue`).
