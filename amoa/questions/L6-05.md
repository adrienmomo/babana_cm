# L6-05 — capture GPS : un vrai service de premier plan Android n'est pas construit ce soir

**Constaté dans le dépôt, pas supposé** : `apps/driver/package.json` ne dépend d'aucune
bibliothèque offrant un vrai service de premier plan Android (`startForegroundService` /
`ForegroundService`, type `react-native-background-actions`,
`react-native-background-geolocation`, ou équivalent). Seuls `@react-native-community/geolocation`
et `react-native-push-notification` existent, déjà utilisés par L6-13 (position ponctuelle) et
L6-12 (alerte de proposition).

## Ce que ça change pour la spécification

L6-05 demande explicitement (« Fonctionnement en arrière-plan avec les permissions et le service
de premier plan requis par Android, avec une notification persistante honnête ») un service de
premier plan **réel**. `apps/driver/src/location/background.ts` pose une notification persistante
(« ongoing », non balayable) qui **donne l'apparence visuelle** d'un tel service, mais ne démarre
aucun lien natif `startForegroundService`. Sans ce lien, Android peut throttler ou suspendre les
minuteurs JavaScript de `tracker.ts` une fois l'application reléguée derrière une autre (Google
Maps, D12) au-delà d'un délai que ce module ne peut ni garantir ni mesurer depuis l'espace
JavaScript seul — le comportement exact dépend de la version d'Android, du fabricant (certains,
comme Xiaomi ou Huawei, imposent des politiques d'économie de batterie encore plus agressives que
le comportement stock d'Android), et de paramètres utilisateur (optimisation de batterie par
application).

## Pourquoi ce n'est pas ajouté ce soir

« Pas de dépendance nouvelle sans nécessité. Si une dépendance lourde semble nécessaire, le
signaler avant de l'ajouter » (CLAUDE.md). Une bibliothèque de service de premier plan est
précisément cette dépendance lourde : elle touche à la fois le code JavaScript, la configuration
native Android (`AndroidManifest.xml`, permissions `FOREGROUND_SERVICE` /
`FOREGROUND_SERVICE_LOCATION` selon la version cible), et n'est vérifiable que sur un vrai
terminal — hors de portée de cet environnement (aucun build mobile, comme déjà noté pour L6-17).
L'ajouter à l'aveugle, sans pouvoir la faire tourner ni la calibrer, serait exactement le genre de
choix qu'il faut signaler plutôt que trancher seul.

## Ce qui a été fait à la place, et ce que ça vaut

- **Adaptatif, agrégé, instrumenté** : les trois exigences vérifiables en JavaScript pur
  (fréquence selon l'état, agrégation avant envoi, compteurs pour L6-17) sont construites et
  testées (`location/adaptive.ts`, `location/tracker.ts`, `__tests__/`).
- **Permissions et repli honnêtes** : premier plan et arrière-plan demandées séparément (Android
  l'exige depuis la version 10), un refus ne bloque jamais l'app, un mode dégradé
  (`LOCATION_DEGRADED_MODE`) applicable par configuration sans réécriture.
- **La notification existe et dit ce qui se passe** — elle ne ment pas sur ce qui est collecté,
  mais elle ne garantit pas, à elle seule, que la collecte continue vraiment une fois l'app en
  arrière-plan prolongé.
- **Ce que ni le code ni les tests ne peuvent prouver ici** : la fiabilité réelle de la capture en
  arrière-plan sur un terminal d'entrée de gamme, avec son propre gestionnaire de batterie. Seul
  L6-17, sur un vrai terminal, le révélera.

## Options, pour le pilote

1. **Mesurer d'abord** (L6-17, sur un vrai terminal) avant de décider si le throttling JS observé
   est un problème réel ou une inquiétude théorique — certains fabricants/versions tolèrent bien
   les minuteurs JS tant qu'une notification "ongoing" existe, avec l'app dans l'onglet des
   applications récentes.
2. **Ajouter une bibliothèque de service de premier plan** si L6-17 montre une perte de capture en
   arrière-plan prolongé inacceptable — nouvelle dépendance native, nouveau build, nouvelle
   configuration `AndroidManifest.xml`, à valider sur le même terminal.
3. **Documenter la limite pour les chauffeurs** (« gardez Babana visible, ne la fermez pas
   complètement ») si le coût d'une vraie dépendance de service dépasse ce que le pilote justifie.

Aucune de ces trois options n'a été tranchée ce soir — c'est une décision qui a besoin d'une mesure
réelle (option 1) avant de pouvoir être prise en connaissance de cause.
