## 1. `ProposalScreen` ne revalide rien auprès du serveur

Le prompt de J27 et le rapport J26 disent tous deux : « `ProposalScreen` revalide déjà auprès du
serveur (D49) : c'est le bon point d'accroche ». **Ce n'est pas le cas.**

Ce que `ProposalScreen` fait réellement (`apps/driver/src/screens/ProposalScreen.tsx`) :

- il reçoit **tous** les détails de la proposition (`origin`, `destination`, `amount`,
  `distanceMeters`, `distanceToOriginMeters`, `expiresAt`) en `route.params`, posés par
  `HomeScreen` à partir du message WebSocket `proposal.new` ;
- il **écoute** ensuite `proposal.accepted` / `proposal.expired` / `session.synced` comme filets
  — mais seulement *après* que le chauffeur a appuyé sur Accepter (`decisionRef.current ===
  'accepting'`) ;
- il n'émet **aucune** requête « cette proposition est-elle toujours active ? » et n'a **aucun**
  moyen d'obtenir les détails d'une proposition qu'il n'aurait pas reçue par `proposal.new`.

D49 et l'écart `L6-12.md` portent sur autre chose : l'ajout du message `proposal.accepted`
comme **accusé de l'action d'acceptation** du chauffeur. Pas sur une relecture de proposition.

`session.resync` → `session.synced` (`services/realtime/src/ws/resync.ts`) ne renvoie que
`activeRideId` + `activeRideState` (états `assigned`/`in_progress`) : **rien sur une proposition
`proposed`**, ni son existence, ni ses détails, ni son `expiresAt`.

## 2. Pourquoi ça bloque L7-04

Le cas central de L7-04 est : **application fermée**, le chauffeur ouvre la notification. L'app
n'a alors jamais reçu `proposal.new` — elle n'a que ce que la notification porte, c'est-à-dire
le minimum voulu par la spécification (« une course est proposée, avec le temps restant » ; pas
de montant, pas de détail, parce qu'une notification peut arriver après l'expiration). Pour
afficher `ProposalScreen` (L6-12), il faut :

1. récupérer les détails de la proposition **depuis le serveur** ;
2. savoir si elle est **toujours active** (sinon : afficher « cette course n'est plus à
   prendre », pas les boutons — critère 3 de L7-04) ;
3. connaître le vrai `expiresAt` pour un compte à rebours **honnête** — cinq secondes s'il
   reste cinq secondes, pas trente fraîches (le prompt insiste là-dessus, et c'est ce que
   « demain matin » attend).

Rien dans le contrat ni dans le service temps réel ne fournit ça aujourd'hui.

## 3. Options

**Option A — le service temps réel ré-émet `proposal.new` à la reconnexion.**
Quand une connexion chauffeur s'établit (ou sur `session.resync`), le service vérifie
`proposalRecordKey`/`proposalRideIdKey` (déjà posées par `propose()`, `services/realtime/src/
proposal/keys.ts`) et, si une proposition est vivante pour ce `driverId`, renvoie `proposal.new`
avec le `expiresAt` recalculé depuis le TTL Redis restant. `ProposalScreen` ouvert « à vide »
depuis une notification affiche un état d'attente jusqu'à ce message ; s'il ne vient pas dans un
court délai (proposition déjà résolue), il affiche « plus à prendre ».
*Coût* : petit changement dans `ws/resync.ts` + `ws/connection.ts` ; `expiresAt` doit devenir
lisible (le stocker dans l'enregistrement, ou le dériver du TTL de `proposalRideIdKey` — qui est
aujourd'hui `RESERVATION_TTL_SECONDS`, pas `PROPOSAL_ACCEPTANCE_TIMEOUT_SECONDS` : à aligner).
*Avantage* : réutilise le message et le chemin d'affichage existants ; aucune nouvelle forme de
requête ; la déduplication par `rideId` déjà en place (`HomeScreen`, « déjà sur Proposal »)
couvre le cas « connecté qui reçoit et le WebSocket et la notification ».

**Option B — un couple requête/réponse dédié** (`proposal.resync` → `proposal.active` |
`proposal.none`).
Plus explicite, mais c'est une nouvelle paire de messages dans `@babana/contracts` pour un
besoin que l'Option A couvre avec l'existant. D50 pousse plutôt vers A (« un flux annonce sa
propre cadence », ici : le serveur ré-annonce l'état, l'app ne le reconstruit pas).

**Recommandation : Option A.**

## 4. Deuxième blocage — le récepteur FCM natif

Comme le service de premier plan (L6-05) et le sélecteur de pièces (L6-15), recevoir une
notification FCM dans `apps/driver` exige un binding natif (`@react-native-firebase/messaging`
ou équivalent) et **un build mobile que cet environnement ne produit pas**. C'est la troisième
dépendance native bloquante. L7-01 a été construite pour que ce soit la *seule* pièce qui
manque côté client : `createPushRegistrar` et le contrat serveur sont réels et testés, le
`PushBinding` réel s'injecte dans la session avec un appareil (voir `amoa/questions/L6-15.md`,
`L6-05.md`).

`apps/driver/src/push/handlers.ts` (fichier listé par la spécification) portera la **logique**
de routage/déduplication d'un message FCM reçu — testable sans SDK — mais le fait qu'un message
arrive réellement se vérifie sur le terminal du pilote.

## 5. Troisième point — la métrique de « délai d'acheminement » (critère 4)

« Le délai entre l'émission de la proposition et l'affichage doit être mesuré. » L'émission est
côté serveur ; l'affichage est côté app. Mesurer *l'affichage* exige que l'app renvoie un signal
(ex. un `proposal.seen { rideId, emittedAt }` sur le fil, ou un champ dans `proposal.accept`).
À défaut, le serveur ne peut mesurer qu'un **proxy** : émission → remise de la notification à
FCM (le `dispatch` de `push.py` renvoyant sans erreur). À trancher : proxy serveur suffisant
pour le pilote, ou vrai aller-retour app→serveur.
