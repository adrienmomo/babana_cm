# L2-04 — le contrat `quote.ts` ne portait pas les champs que sa propre spécification exige

**Développée cette nuit (J5), sur `master` directement**, comme les tâches de J4
(`amoa/questions/L4-03.md`, `amoa/questions/L4-11.md`).

---

## Contradiction entre C-01 (`quote.ts`, déjà arrêté) et la spécification de L2-04

`amoa/specs/L2-tarification.md`, L2-04, exige :

- une requête portant « départ, arrivée, **gamme souhaitée**, code promo éventuel » (critère
  implicite, gamme nécessaire à la sélection de règle et à la distance) ;
- une réponse dont « le détail décomposé est complet » (critère 4) ;
- un indicateur explicite quand un code promo est invalide plutôt qu'une erreur (critère 5).

`packages/contracts/src/http/quote.ts`, tel qu'arrêté par C-01, ne portait aucun des trois :
`QuoteRequestSchema` n'avait que `origin`, `destination`, `promoCode` ; `QuoteResponseSchema`
n'avait ni détail décomposé ni indicateur de remise. Une contradiction entre une spécification de
tâche et un contrat déjà arrêté justifierait normalement un arrêt (protocole d'écart, CLAUDE.md).
Décidé de ne pas arrêter et d'étendre le contrat plutôt, pour trois raisons : l'extension est
strictement additive (aucun champ retiré, aucun type resserré, un appelant déjà écrit contre
l'ancien schéma continue de compiler) ; le même geste a déjà un précédent accepté sans arrêt
(L4-03 a ajouté `public_id` aux modèles et `DRIVER_NOT_APPROVED` au catalogue d'erreurs sans
qu'aucune spécification ne les ait demandés explicitement, `amoa/questions/L4-03.md`) ; et
refuser d'implémenter L2-04 faute d'un champ de contrat manquant aurait bloqué tout le lot de
cette nuit pour une extension mécanique, pas une question de conception.

**Ajouté à `quote.ts`** :
- `vehicleClass` (optionnel, `'standard' | 'premium'`) sur `QuoteRequestSchema`.
- `breakdown` (`FareBreakdownSchema`, miroir de `FareBreakdown` de `services/pricing.py`) et
  `promoApplied` (booléen) sur `QuoteResponseSchema`.
- `ROUTE_UNAVAILABLE` au catalogue d'erreurs (`errors.ts` + `QuoteErrors`), mappé 503 : L2-05
  exige une erreur explicite quand l'API de routage est indisponible (critère 3), le catalogue
  n'avait aucun code pour ce cas.

Si ces champs sont jugés à leur place ailleurs (un fichier séparé, un nom différent), le
signaler — c'est un choix d'implémentation, pas une décision d'architecture.

## Facteur de correction d'ETA (L10-03) : valeur provisoire, pas un calcul inventé

La spécification demande d'« appliquer le facteur de correction d'ETA (L10-03) », mais L10-03 —
qui calibrera ce facteur sur données de pilote réelles, comme L2-05 le renvoie lui-même vers
L10-05 pour le choix distance de référence / distance parcourue — n'existe pas encore et n'est
pas dans le périmètre de cette nuit.

Retenu : un paramètre système `babana.eta_correction_factor`, valeur par défaut `1.0` (aucune
correction), explicitement documenté comme provisoire (D21) dans `controllers/quote.py`. La durée
brute du routeur passe bien par cette étape (critère d'acceptation 3 satisfait mécaniquement,
vérifié par `test_eta_is_corrected_not_raw` avec un facteur non trivial), mais la valeur réelle du
facteur reste à calibrer par L10-03. Paramétrable (invariant 5), jamais codé en dur.

## Code promo : toujours sans effet, faute de `babana.promotion` (L2-06)

L2-06 (le modèle `babana.promotion`) n'est pas dans le périmètre de cette nuit. `POST /quote`
accepte donc `promoCode` sans jamais pouvoir le résoudre : `promoApplied` vaut toujours `false`,
`discountAmount` toujours `0`, quel que soit le code fourni — jamais une erreur, ce qui satisfait
littéralement le critère d'acceptation 5 (« un code promo invalide n'échoue pas la cotation »)
même si la vraie logique de validation (code existant, expiré, épuisé, limite par client) n'existe
pas encore. Le champ `babana.quote.promo_applied` existe déjà, prêt pour que L2-06 n'ait qu'à
brancher sa résolution.

## Arrondi du détail décomposé sur le fil HTTP : `roundingAmount` absorbe deux arrondis, pas un

`MoneyAmountSchema` (`packages/contracts/src/http/common.ts`) exige un entier — XAF n'a pas de
sous-unité. `FareBreakdown` (L2-03, `services/pricing.py`) est en revanche calculé en flottant, et
ses composantes individuelles (`distance_fare` notamment, fonction d'une distance en kilomètres
non nécessairement entière) peuvent porter une fraction de FCFA que seul `rounding_amount`
absorbe pour que la somme égale exactement `total` (critère 4 de L2-03, `sum_matches_total()`).

Arrondir chaque composante indépendamment à l'entier pour le fil JSON casserait cette identité.
`controllers/quote.py:_round_breakdown_for_wire()` arrondit donc `base`, `distance`, `surge`,
`discount`, `floor` et `total` indépendamment, puis calcule `roundingAmount` par différence —
il absorbe alors à la fois l'arrondi au pas configuré (son rôle initial, côté pur) et l'arrondi
entier d'affichage. Le détail brut (flottant, non arrondi à l'entier) reste seul stocké dans
`babana.quote.fare_rule_snapshot`, qui fait foi en cas de litige — ce que le client voit dans la
réponse HTTP est une projection d'affichage, pas la source de vérité.

## Ce qui reste hors de portée, assumé

Le critère d'acceptation 6 de L2-04 (« la course créée depuis une estimation porte ses zones de
départ et d'arrivée, ainsi que la référence de la règle tarifaire appliquée ») ne peut être
vérifié que par L4-03R (`POST /rides`), qui n'existe pas encore au moment où ce fichier est écrit.
`test_quote_controller.py` le documente en tête de fichier et laisse la vérification effective à
`test_ride_controller.py` une fois `POST /rides` implémenté plus tard cette même nuit.
