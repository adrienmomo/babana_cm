# L0-01 — infrastructure Docker

## Écart — le `Caddyfile` donné en exemple (`04-monorepo-et-services.md` §7) ne sert pas le
fichier qu'il prétend servir

**Hypothèse retenue (appliquée dans le code) :** ajout d'une directive `uri strip_prefix
/.well-known` dans le bloc `handle /.well-known/assetlinks.json` de
`code/infra/caddy/Caddyfile`, absente du snippet donné.

**Ce que demande la spécification.** L0-01 dit d'implémenter le `Caddyfile` « tel quel » depuis
`amoa/04-monorepo-et-services.md` §7. Le bloc donné est :

```
handle /.well-known/assetlinks.json {
	root * /srv/wellknown
	file_server
}
```

**Pourquoi cela pose problème.** `root` change la racine de fichiers utilisée par `file_server`,
mais ne réécrit pas le chemin de la requête. Avec `root * /srv/wellknown` et une requête sur
`/.well-known/assetlinks.json`, `file_server` cherche
`/srv/wellknown/.well-known/assetlinks.json` — pas `/srv/wellknown/assetlinks.json`, où le
fichier se trouve réellement d'après l'arborescence donnée par L0-01
(`infra/caddy/wellknown/assetlinks.json`, monté sur `/srv/wellknown` par `compose.yaml`).
Résultat vérifié en local : `404` sur `curl -k https://localhost/.well-known/assetlinks.json`,
alors que le fichier existe bel et bien dans le conteneur. C'est exactement le défaut que
`amoa/04-monorepo-et-services.md` §6 décrit comme critique : « Sans ce fichier, les
notifications qui ouvrent l'app sur le bon écran déclencheront un sélecteur d'application au
lieu d'ouvrir babana directement » — sauf que le fichier n'est pas seulement absent, il est
présent mais inatteignable, ce qui est plus trompeur à diagnostiquer en production.

**Options considérées.**

1. **Retenue.** Ajouter `uri strip_prefix /.well-known` avant `file_server`, pour que le chemin
   restant (`/assetlinks.json`) corresponde à l'emplacement réel du fichier sous la racine.
   Vérifié : `curl -k https://localhost/.well-known/assetlinks.json` renvoie `200` après ce
   changement (voir `infra/smoke-test.sh`, critère d'acceptation 6 de L0-01).
2ᵉ option écartée : monter `infra/caddy/wellknown/` sur `/srv/wellknown/.well-known/` dans
   `compose.yaml` plutôt que sur `/srv/wellknown/`. Rejetée : cela aurait contredit
   l'arborescence de fichiers donnée par L0-01 lui-même (`infra/caddy/wellknown/
   assetlinks.json`, pas `infra/caddy/wellknown/.well-known/assetlinks.json`), pour corriger un
   défaut qui vit dans le Caddyfile, pas dans la structure de dossiers.

**Recommandation.** Corriger le bloc `/.well-known/assetlinks.json` de
`amoa/04-monorepo-et-services.md` §7 pour inclure `uri strip_prefix /.well-known`. Le reste du
Caddyfile donné (blocs `api.` et `admin.`) a été vérifié fonctionnel tel quel cette nuit
(`infra/smoke-test.sh`, exécuté avec succès contre la pile réelle).

## Urgence

Non bloquant pour la suite : la correction est appliquée dans le code et vérifiée. À corriger
dans le document de référence pour que la prochaine personne qui transcrit ce Caddyfile "tel
quel" ne reproduise pas le même 404.

## Note — services placeholders créés en avance de L0-02/L0-04/L0-08

Non un écart de spécification, mais une décision de séquencement à consigner : le `compose.yaml`
donné par `04-monorepo-et-services.md` référence `services/realtime/Dockerfile` et (via
`compose.dev.yaml`) `services/mocks/*/Dockerfile`, qui n'existent normalement qu'à l'issue de
L0-04 et L0-08 — deux tâches plus tardives dans le lot de cette nuit. Sans ces fichiers,
`make up` ne peut pas produire les « sept services sains » exigés par le critère d'acceptation 1
de L0-01 lui-même.

Hypothèse appliquée : créer ce soir, dans L0-01, des squelettes minimaux et clairement marqués
comme tels (un serveur HTTP qui répond `200` sur `/health`, rien d'autre) pour
`services/realtime` et `services/mocks/{google-identity,maps}`, afin que `make up` fonctionne
réellement dès L0-01. L0-04 et L0-08 remplaceront entièrement ces squelettes par les
implémentations spécifiées — ce n'est pas anticiper leur contenu, seulement débloquer le critère
de fin de L0-01 sans attendre trois tâches supplémentaires.
